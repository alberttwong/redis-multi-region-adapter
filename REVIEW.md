# Review guidance

Use [spec.md](spec.md) as the contract, [plan.md](plan.md) for implementation scope, and [validation.md](validation.md) for evidence. Production APIs are proposed; legacy spike behavior is distinct.

## Review passes

1. **Available race:** every captured group member, including local, starts concurrently. Return first valid non-null value immediately; a null reply does not stop pending attempts. Return null only on all-null completion or the shared deadline without a value. No newest-value comparison, quorum, repair, or sequential fallback.
2. **Local and errors:** Local contacts one regional endpoint. Validate authorization, binding, integrity, generation, and expiry for both reads. Preserve Local infrastructure errors and request-level configuration/access errors; Available per-target failures do not cancel healthy attempts. Distinguish deadline-null from confirmed all-null in telemetry.
3. **Resource lifecycle:** shared bounded deadline, bounded group fan-out/pools, cancellation, and disposal of loser/late replies. A winner must not await slow cleanup. Group membership is fixed per operation and includes local; unauthorized or malformed overrides fail before dispatch.
4. **Write/distribution:** stable IDs, immutable envelopes, no repeated business mutations on fan-out, original expiry, uncertain-write reconciliation, no background repair for independent clusters, and Redis-managed recovery for Active-Active. Reject obsolete recovery selectors. All-target success verifies the entire captured target set and does not establish linearizability. Later same-session writes fan out current values as normal write behavior; preserve legacy spike replay experiments separately.
5. **Monotonic modifier:** default false; true composes with Local (only local) or Available (group search). Reject a standalone monotonic policy and unimplemented/invalid modifier values; never silently ignore true. Automatic last-successful-read floors must survive caller movement and cannot roll back through concurrent responses. Reject older/incomparable state without history proof. An established unexpired floor cannot yield arbitrary null/stale success; wait or fail. Off-reads must not lower a retained floor; strategy changes must not reset it. Distinguish first reads from lost floors, and define deletion/absence/expiry/generation ordering. Describe the enforced floor as last-observed freshness, distinct from linearizable real-time freshness; no RYOW/latest-write or maximum-age claim.
6. **Linearizable/custom scope:** both implementations carry **slow++** read/write planning ratings; do not present these as measured latency guarantees. Both linearizable modes need validated real-time commit/read/fencing/failure protocols. Native causal consistency is backend configuration only; Causal is not a public read option or custom protocol workstream. Reject unimplemented/removed policies rather than downgrade.
7. **Scope and evidence:** no production Session option, caller write-context automation, or public exact-version selector. Read groups do not shrink write obligations. Active-Active provides eventual convergence. Historical spike tests/results are not production acceptance for group-racing Available.

## Severity and completion

Critical findings expose secrets, cross caller/security boundaries, or bypass authorization. Important findings violate the documented race, return early null, accept invalid state, leak unbounded work, or make false ordering/durability claims. Minor findings concern clarity or maintainability without behavioral impact. Confirm the five-region/six-client sizing and review actual measurements/tests rather than proposed scenarios alone.

Local and Available inherit same-key causal operation ordering when Active-Active causal consistency is enabled. This backend ordering does not ensure a region has caught up or prevent a caller from reading older state after switching regions. With monotonic on, both strategies additionally enforce per-caller same-key non-regression using automatic read history; independent clusters need that enforcement too. Neither causal ordering nor monotonic reads guarantees the latest completed write. Same-key Redis ordering must not be assumed to order multiple snapshot/hint keys.

Review scope: prefer Redis Enterprise native capabilities and existing client facilities for data/conflict semantics, persistence/durability, expiration, capacity, pools, and timeouts. Reject unsolicited replacement features or group/clock/resource/service-level subsystems. Baseline adapter fan-out, deadline/cleanup handling, validation, and identity preservation remain required. Monotonic and Linearizable remain deferred custom extensions.
