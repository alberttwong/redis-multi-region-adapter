# Plan: Local and Available adapter

Date: 2026-11-09. Status: production implementation proposed; Available is default.

## Starting point

The repository contains design documents and a legacy [Python/AWS/Terraform spike](spike/README.md). Its old read controls and measurements do not implement the new group-racing Available behavior. The adapter must build on top of, or work with, the [official Redis clients](https://redis.io/docs/latest/develop/clients/), initially **Jedis for Java** and **redis-py for Python**. Exact client versions, middleware, packaging, and CI remain unselected. Paths below are proposals for each language implementation.

## Order of work

1. Finalize [spec.md](spec.md) using Redis Enterprise native capabilities and official Redis client integrations, initially Jedis for Java and redis-py for Python. Define public client API integration, application-supplied client/pool support, and resource ownership. Record native conflict/expiry/persistence behavior, configured groups/overrides, client pool limits, and request deadlines. Do not build replacement database features, custom skew correction, dynamic group management, or service-level enforcement. Session context/RYOW automation is removed from scope.
2. Pin the deployed Redis Software 8.x build, supported commands/data types, selected official-client dependency versions (initially Jedis and redis-py), three primaries per regional database plus replicas, native persistence/expiration/capacity settings, and endpoints. Configuration and capability verification do not require custom implementations. Keep provisioning and benchmark authorization separate from implementation work.
3. Derive delivery recovery from distribution: independent clusters have no background repair; Active-Active uses Redis-managed replication. Reject obsolete recovery selectors. Add `src/config/`, `src/clients/`, `src/topology/`, and `src/records/`: pooled connections, immutable identity/content/expiry, valid local candidate lookup, group membership including local, and captured epochs/targets.
4. Add `src/distribution/` for idempotent, bounded request-time independent fan-out of each update's current version. Do not add an outbox or background repair worker. Active-Active uses native transport. Preserve local versus all-target acknowledgment semantics.
5. Add `src/reads/local/` and `src/reads/available/`. Local performs one regional lookup. Default Available concurrently starts every group request including local, accepts the first valid non-null value, continues after null/failed attempts, returns null on all-null or deadline, and cleans up losers without delaying the winner. There is no public historical/version selector or client write-context path.
6. Add contract, integration, fault, and load tests following [validation.md](validation.md). Run the same contract scenarios against every supported official-client integration, initially Jedis and redis-py. Verify supplied clients/pools retain caller ownership and client facilities enforce configured bounds. Exercise first-null/later-value, stale-first wins, local wins, all-null, deadline-null, failed members, group changes, cancellation, and resource bounds against real deployments.
7. Measure Local and Available separately, including winning region, outcome rates, pending/failed attempts, pool load, and complete end-to-end histograms. Follow [latency.md](latency.md); historical spike p99 is not a prediction for the new fan-out path.
8. Rehearse expiry, uncertain-write reconciliation, restart/restore, target admission, configuration changes, rollback, and cleanup. Replace proposed operations with verified commands and sanitized evidence.

## Effort estimates

**Effort:** S = bounded feature; M = moderate concurrency/resource handling; L = substantial automatic history and correctness work; XL = distributed protocol and failure/recovery validation. Estimates assume shared clients, authorization, validation, and topology plumbing; they exclude infrastructure and a complete production SDK. The L history feature is shared by Local/Available, and linearizable read/write work is shared too, so sizes are not additive. Stronger-guarantee estimates have low confidence until the designs are selected.

## Risks and limits

Key risks are returning null after only one miss, waiting for all members after a value wins, dispatching sequentially, accepting invalid values, unbounded fan-out/loser work, falsely claiming fresh/latest state, and shrinking write targets because a read group was selected. Neither supported read guarantees RYOW or linearizability. Future monotonic-modifier work (boolean default false, on Local/Available) needs automatic per-caller read-floor retention/transport, safe concurrent response sequencing, accepted version/history evidence, local-only or group candidate filtering according to the base strategy, safe on/off/strategy transitions, and bounded wait/failure handling across both backends. Define absence, deletion, expiry, and generation behavior first. No unread-write RYOW or latest-state guarantee is implied. Both Linearizable implementations need validated authority/commit/read/fencing/failure protocols targeting the same real-time per-key guarantee. Causal/custom causal protocols are removed as application options; the native flag is only backend configuration. Both Linearizable implementations are budgeted as **slow++** for reads and writes until validated protocol measurements replace the planning bands. Available remains default. Current cross-device revocation and cross-session transactions remain separate designs.
